# セキュリティ — 何が守られていて、何が守られていないか

SSH クライアントは、接続先のパスワードや秘密鍵を預かり、その鍵で任意のコマンドを
実行できる端末になる。守れている範囲と、仕組み上どうにもならない範囲を分けて書く。

## 1. 資格情報の保護

- **暗号化して保存する。** パスワードと秘密鍵の本体は `filesDir/secrets/` に
  `<secretId>.bin` として置き、Android Keystore の鍵（`MasterKey`,
  `AES256_GCM`）で `EncryptedFile`（`AES256_GCM_HKDF_4KB`）により暗号化する。
  平文で書き出す経路はない
- **復号した値は認証のためだけに取り出し、直後に消す。** SSH 認証には平文が要るので
  取り出すこと自体は避けられない。代わりに保持時間を自分で制御できる形にしてある:
  - パスワードは `loadPassword` から `CharArray` で返り、`SshChannel` が
    `authPassword` に渡した直後に `finally` でゼロ埋めする。`String` は不変なので
    一度作ると GC まで残り、メモリダンプから読める。`CharArray` なら消せる
  - 秘密鍵のバイト列とパスフレーズも同様に、認証完了後にゼロ埋めする
  - 秘密を持つデータクラスは `toString()` を封じてある。`data class` の既定実装は
    中身をそのまま出すので、ログに一行書かれるだけで漏れる
  - sshj が内部に持つコピーは接続維持に要るため残る。ここは制御できない
- **復号に失敗しても落ちない。** ファイルの破損や Keystore の鍵無効化で復号できない
  場合は `null` を返し、「認証情報が見つからない」として扱う。例外を投げると接続
  ボタンを押しただけでアプリが落ちる。復号できないレコードを自動削除はしない
  （一時的な失敗と恒久的な失敗をこの層では区別できないため）
- **バックアップと端末間移行から除外する。** `backup_rules.xml` と
  `data_extraction_rules.xml` の `cloud-backup` / `device-transfer` で
  `secrets/`・`anoterm.db`・`anoterm_prefs.xml` を除外している。
  `allowBackup=false` だけでは一部メーカー端末の移行を止められないため。
  なお Room の WAL ファイル（`anoterm.db-wal` / `-shm`）と Tink の鍵セットを収める
  設定ファイルは、この列挙に含まれていない。鍵セット自体は Keystore で保護されて
  いるため平文の流出にはならないが、「すべて」ではない
- **ログに出さない。** パスワード・パスフレーズ・秘密鍵をログに渡している箇所はない。
  ただしホスト名・ポート・鍵種別は、鍵の変化を検知した際に警告として記録する。
  sshj の例外メッセージにもホスト名と指紋が含まれることがある
- **アプリロック（生体認証）は任意。** 有効にすると、起動時と、背面から戻った
  ときに認証を要求する。背面にいてよい時間は設定で選べる（既定 30 秒、即時も可）。
  猶予の判定には `SystemClock.elapsedRealtime` を使う。壁時計だと端末の時刻を
  進めるだけで回避できてしまうため。ただしこれは UI の入口を塞ぐだけで、
  **Keystore の鍵自体にユーザー認証を要求していない**。後述の限界を参照
- **認証が一時的に使えないときは解錠しない。** センサーが塞がっている等で
  `canAuthenticate` が失敗した場合、素通りさせればセンサーを覆うだけで
  ロックを回避できる。この場合は解錠を拒み、再試行を促す。例外は生体も画面ロックも
  一つも登録されていない端末で、照合する相手が存在しないため解錠する（記録は残す）
- **スクリーンショットと「最近使ったアプリ」のサムネイルを既定で禁止する。**
  `FLAG_SECURE`。設定で解除できる

## 2. 接続先の検証（TOFU）

`HostKeyVerifier` は Trust On First Use。

| 状況 | 動作 |
|---|---|
| そのホストの記録が無い | 鍵を記録して接続する |
| 記録と指紋が一致 | 接続する |
| **記録と指紋が不一致** | **拒否する**（警告して続行する経路は無い） |
| **記録はあるが別の鍵種別** | **拒否する** |

最後の行が重要である。照合を `(ホスト, ポート, 鍵種別)` で行うと、ed25519 を記録済みの
ホストに攻撃者が ecdsa を提示するだけで「未知のホスト」と判定され、警告なく自動信頼
されてしまう。鍵交換でどの種別を提示するかを決めるのは相手側なので、これは実質的な
迂回路になる。そのためホスト単位で記録の有無を見て、記録があるなら一致を要求する。

あわせて記録済みの鍵種別を sshj に伝え、host-key algorithm の提案順を既知の種別優先に
並べ替えさせている（`findExistingAlgorithms`）。正規のサーバーとは記録済みの種別で
鍵交換が成立しやすくなる。

鍵が変わったときに黙って受け入れないことが、この実装の要点である。中間者攻撃は
まさにそこで検知される。初回接続時は検証の対象がないので、**最初の接続だけは
信頼に基づく**。重要なホストは、初回接続後にフィンガープリントを別経路
（サーバー側で `ssh-keygen -lf`）で突き合わせること。

## 3. 通信

- SSH（sshj 0.40.0）による暗号化通信のみ。生 socket を直接扱う
- **弱い暗号方式を提案しない。** sshj の `DefaultConfig` をそのまま使うと、鍵交換に
  group1-sha1 / group14-sha1、暗号に Blowfish・CAST5・IDEA・3DES・Arcfour、MAC に
  HMAC-MD5 が提案リストに載る。これらは、そのうち一つしか受け付けないサーバー
  （あるいは中間者）に合わせてダウングレードが成立する余地になる。採用しているのは
  次のみ:
  - 鍵交換: curve25519-sha256、ecdh-sha2-nistp256/384/521、
    diffie-hellman-group-exchange-sha256
  - 暗号: aes256/192/128-ctr
  - MAC: hmac-sha2-256、hmac-sha2-512
- `network_security_config.xml` は cleartext を既定で禁止し、system CA のみを信頼する。
  **例外は `127.0.0.1` の 1 つだけ**（後述のポート転送の出口）。SSH は CA を使わないが、
  将来 HTTP 呼び出しが混入した場合の防波堤として明示している
- 権限は `INTERNET` / `ACCESS_NETWORK_STATE` / `USE_BIOMETRIC` / `VIBRATE` /
  `POST_NOTIFICATIONS` / `FOREGROUND_SERVICE(_SPECIAL_USE)` のみ。
  ストレージ・連絡先・位置情報は要求しない

## 3-2. ポート転送とページの表示

端末に出た `http://` の URL を押すと、この SSH 接続の中を通してそのページを表示する。
広げた面はこの 2 つ。

- **ローカルポート転送（`LocalForward`）。** 端末側の **`127.0.0.1` の空きポートにのみ**
  待ち受ける（`0.0.0.0` では開かない）。同じ Wi-Fi にいる第三者からは届かない。
  転送先は SSH サーバーが解決するので、`localhost` は接続先自身を、それ以外は
  接続先から見えるアドレスを指す。面を閉じれば穴も閉じる
- **`WebView`。** JavaScript と DOM Storage を有効にしている（開発サーバーの中身は
  まず JS で動くため）。表示先は転送の出口 `127.0.0.1:<ポート>`、
  つまり SSH の中を通った先だけ。**ただし `https://` は転送しない** —
  転送すると宛先が `127.0.0.1` になり証明書の名前が合わないため、端末から直接開く。
  これが、このアプリが SSH 以外の通信を行う唯一の経路である

`cleartext` の例外を `127.0.0.1` に限っているのは、ここを 1 つに絞っておけば、
意図しない宛先が紛れ込んでも素通りしないため。`localhost` という綴りは入れていない。

## 3-3. リモートのファイルの読み出し

端末に出たパスを押すと、その中身を読んで表示する（画像・文書）。

- 読み出しは **対話シェルとは別の SSH セッション**（`exec`）で行う。利用者が作業して
  いるコマンドラインに `base64` などが混ざらない
- 送るのは `wc -c` と `base64` のみ。**パスは必ずシェルクォートを通す**
  （`ScreenScan.shellWord`。`'` を含むファイル名でもコマンドが割れない）
- 大きさを先に見て、画像 5 MB / 文書 1 MB を超えるものは読まない。
  画像は長辺が 2048px を超えないよう間引いて展開する
- 相対パスは tmux のペインの現在地 → ホームの順に探す。見つからなければ開かない

## 4. 他アプリからの操作

- `MainActivity` のみ `exported="true"`（ランチャー起動のため）
- `SshForegroundService` は `exported="false"`
- 外部から接続先やコマンドを指定できる Intent フィルタは公開していない

## 5. 塞げていないもの（仕組み上の限界）

- **端末のロックを破られた場合、資格情報は取り出されうる。** Keystore の鍵に
  ユーザー認証を要求していないため、アプリのプロセスとして動けば復号できる。
  アプリロックを有効にしていても、それは UI の入口であってデータの鍵ではない
- **root 化された端末では保護は成立しない。** `filesDir` を読める主体は
  Keystore にも到達しうる
- **初回接続は検証できない。** TOFU の構造上、最初の鍵を信じるほかない
- **接続先サーバーの安全性はこのアプリの範囲外。** SSH は認証された相手との
  暗号化通信を提供するだけで、その相手が誠実かどうかは保証しない
- **`FLAG_SECURE` は万能ではない。** スクリーンショットと最近使ったアプリの
  サムネイルは塞ぐが、他アプリのオーバーレイ表示や、物理的に画面を覗かれること、
  root を取られた端末での画面取得までは防げない
- **sshj と Bouncy Castle の脆弱性はこのアプリの範囲外。** 更新に追随する以上の
  ことはできない
- **`WebView` が表示するページは、接続先サーバーが返す内容そのものである。**
  自分の開発サーバーを見るための機能であり、任意のサイトを安全に閲覧するための
  ブラウザではない。JavaScript も有効である
- **`https://` のページは端末から直接取得する。** SSH の中は通らない。
  ここだけは接続先を経由しない通信になる

## 6. 意図的にやっていないこと

- **ホスト鍵の変更を「警告して続行」にしない。** そこで止まらなければ TOFU に
  意味がない。鍵を張り替えた場合は、既知ホストの記録を明示的に削除する
- **資格情報をクラウドに同期しない。** 同期は端末間移行の利便性と引き換えに、
  鍵の置き場所を一つ増やす
- **パスワードを自動入力・自動再送しない**
- **ロック中も接続は維持する。** 再ロックで SSH を切ると、少し目を離した
  だけで実行中の処理が落ちる。ロックは画面を覆うだけで、セッションには触れない

## 7. 分かっている改善余地

対処していないが、認識している点。

- **UI の入力欄は `String` を経由する。** Compose の `TextField` が `String` を
  要求するため、利用者が打ち込んだ直後の値は不変文字列としてヒープに乗る。
  保存時に暗号化され、読み出し以降は `CharArray` で扱われるが、入力から保存までの
  区間だけは制御できていない
- **端末に生体情報も画面ロックも登録されていない場合、アプリロックは素通りする。**
  ロック手段が無い端末で締め出さないための挙動だが、保護としては成立していない
- **ロック中でも通知は出る。** 常駐通知にはセッション数が出る。接続先名までは
  出さないが、使用中であることは画面を解錠せずに分かる。通知の「すべて切断」も
  解錠せずに押せる（読まれるのではなく切られるだけなので、実害は作業の中断に留まる）
